# Review 5 — ADR-0016 restore drill change set (post-v0.9.0), 2026-09-20

Four-role review (Staff development engineer / Product engineer / Security engineer / CTO)
of the ADR-0016 change set (`7dad410..HEAD` on `adr-0016-restore-drill`): the table
classification in `schema.py`, `scripts/restore_drill.py`, its tests on both tiers, the
`restore-drill` CI job, and the RUNBOOK / LONGEVITY / SLO changes. The surfaces earlier
passes never reached: backup and recovery, the enforced-vs-policy honesty of the charter,
and a script that creates and drops databases.

Method: the code-reviewer skill as an **independent agent with no shared context**,
read-only, over the risk-ordered core diff (`scripts/restore_drill.py`, `schema.py`,
`ci.yml`, tests), asked eight pointed questions (vacuity, classification, comparison
pitfalls, destructive-path safety, global state, CI, discrimination, SQLite consistency);
a four-role debate per finding; every accepted finding fixed with a test or a live
demonstration that fails on the old behaviour; `code-quality-analyzer 3.1.0` before
(`7dad410`, via a worktree) and after. Self-review of the fixer's own commits included
(it caught the environment leak before the independent pass ran).

## Candidates considered and dismissed

| Candidate | Raised by | Why declined |
|---|---|---|
| Seed one poison event so `dead_letters` is non-empty and the subset criterion is exercised | Independent reviewer (F3 fix suggestion) | The only way to plant a poison event is to write a row to `events` outside the command path (a `schema_version` newer than the build, ADR-0009). That stream then **cannot be folded by this build by design** — `fold_all` would raise on it, and teaching the drill to skip unfoldable streams hides exactly the class of failure it exists to catch. The consumer's poison-event tests already prove re-dead-lettering on both tiers; labelling the criterion honestly (F3) is the right fix at this scale. Revisit if a production dump with real dead letters is drilled (`--dump` mode exercises it). |
| `tuple(r)` of a psycopg dict row would compare column names, not values | Reviewer, self-dismissed | The drill uses raw `psycopg.connect()` (tuple rows), not the adapters' `open_pool()` (dict rows); `r[5] == "open"` indexing confirms. |
| Fold `version` vs read-model `version` could legitimately differ | Reviewer, self-dismissed | Both increment once per event on the account's own stream; the seeded PG drill passing on 8 streams confirms. |
| `DROP DATABASE … WITH (FORCE)` could hit a non-drill database | Security | Only names generated with the `cloudscale_drill_` prefix ever enter `_created`; `--dump` mode never drops the source; `--source-dsn` is read-only (`SELECT MAX(id)`). |
| The drill TRUNCATEs derived tables — could that reach the live database? | Security / CTO | TRUNCATE runs only against the freshly created restored database; the source DSN is only ever dumped or read. On SQLite each `DELETE FROM` is guarded by a `not in schema.DERIVED → ToolingError` refusal. |
| The seeded drill's RTO numbers are tiny and could be quoted as production RTO | Product / CTO | `docs/SLO.md` § Recovery states "measured at seeded scale only … not promised" until a production-scale report exists; the ADR and CHANGELOG say the same. |
| `--exit-on-error` on `pg_restore` may fail a legitimate restore on harmless warnings | Staff | Deliberate: a drill must not pass with a partially restored database; the tooling error (exit 2) names the stderr tail so an operator can decide. |
| Missing pipefail on the pre-existing gate step as a separate finding | Reviewer | Same root cause as F2; fixed by the same workflow-level default. |
